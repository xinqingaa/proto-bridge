# 一刻

一刻是本机使用的专注与习惯工具，包含番茄钟、正计时、倒计时、习惯打卡和周月回顾。

## 文档职责

| 文档 | 负责什么 |
| --- | --- |
| [产品说明](product.md) | 产品定位、范围、页面职责、导航与核心使用路径 |
| [逻辑与交互](logic-and-interactions.md) | 业务对象、数据流转、状态机、保存恢复、统计及异常反馈 |
| [UI 与动效设计](ui-design.md) | 页面结构、滚动边界、主题图形、资源复用、动效及可访问性 |
| [已知缺口](known-gaps.md) | 原型实现偏差、待决事项、目标准备情况和未验证边界 |

先读产品说明，再按任务阅读逻辑与 UI 文档，并核对已知缺口。四份文档按职责展开同一份产品基线，不用计划或实现现状静默改变要求。[design.md](design.md) 保留既有已批准的产品原文，本次未改动；新增说明不自动批准新的业务行为。

## 维护与交付方向

产品文档的源头是本目录：先在 `proto-bridge/apps/pbwork/src/prototypes/yike/docs/` 写完整，再随创建/生成与同步流程复制到独立 `yike/docs/`。目标工程读取自己的本地副本，产品文档不通过 MCP 获取，也不由目标工程反向维护原型源文档。

自动复制脚本后续接入，本次只补全源文档；在接入前由用户手动复制。后续脚本应保留这组文档的同目录链接，并与目标工程已有的架构、组件、主题、资源和测试规范共存，避免覆盖工程文档。现有独立 yike 工程中已写好的内容本次不动。

固定 Case、Screenshot 和交互证据继续走 Handoff/MCP；复制文档不等于固定 Evidence，也不自动具备同一版本。遇到产品要求与固定观测冲突，记录双方来源；文档中的动效意图不能作为真实过程采集已通过的证明。

[整改范围记录](delivery-upgrade-plan.md) 维护实施范围及已知问题，不承担产品规则定义。文档 Catalog、文档 MCP 和真实动效采样平台仍不属于当前补全文档工作。
