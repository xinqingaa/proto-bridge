## 主线与范围

按「先从草稿提取主题与组件 → 用验证过的资源制作页面 → 每完成一页与草稿对比」推进。先做全局盘点，主题与 DS 适配按页面依赖推进；原型专属内容直接在页面上下文制作与对比，不以建成独立组件库或完成所有资源预览作为页面开工条件。无需等所有页面完成才验收，也不反复开启视觉采访。

输入是 [design.md](./design.md) 的批准契约与 `drafts/yike/styles/` 的三套完整风格，保留机械、水位、日影及浅深两种模式，字体统一默认系统字族。首次为零历史和四个预置习惯；草稿的有数据状态另用确定性 fixture 准备。

最终范围为启动、专注、打卡、习惯详情、新建/编辑习惯、回顾、设置七个业务页面，以及支撑演示的最小共享状态、Runtime 状态、Evidence 和整原型定稿。Flutter Target 还原不在本轮范围。

平台计划不再作为一刻的待办。实际遇到平台能力缺陷时，在唯一问题表记录最小复现与影响；必要的通用修复另归平台权威手册，不新建一套一刻升级计划。

## 主题与归位确认清单

本清单落实用户批准的详细范围；实施状态仅在implementation.md维护。

- 三主题共用页面、状态、导航与DS实现，各保留浅深模式。机械保留柿色、刻度与孔；水位保留苔绿、水体与滴；日影保留靛蓝、纸面软影与印。主题参数表达字阶、圆角、染色与高光，不复制三套页面。
- 明确玻璃区域：根导航、局部切换、设置分组、习惯卡行、详情概况、回顾总结、当天记录和共享面板。主按钮先保证强调与对比；表盘、水体、纸面和图表标记保留签名材质。避免内部逐层叠玻璃，保留实色降级。
- DS归位范围：Tabbar、SegmentedControl、Button、IconButton、GroupedList/ListCell、Metric、TextField/Stepper/Switch、DurationPicker、共享Sheet/Confirm/Toast、MonthCalendar、Heatmap。具体归属及缺口见resources.md。
- 原型本地范围：三表盘、打孔卡行与标记、轮次计圈、业务表单、三形态周图、面板业务内容以及共享业务数据。不为这些内容新增Workbench独立组件条目。
- 下一实施依赖：文档纠偏与控件归位 → 共享业务状态/壳 → 七页逐页接入、草稿对照 → 六组合与整体旅程验证。已有成果继续使用，不等待独立资源展台完成。

本轮没有阻塞 D 阶段的产品未决项。Flutter Target App 身份留到还原前确认；既有 DS→Target drift 独立记录，不能靠刷新 baseline 伪造通过，也不能将该项当作七页停止制作的理由。D 全部验收后接续 E 的整体门禁与固定交付；页面验收、整体验收、生命周期定稿分别记录结果。

1. 准备相同主题、模式、逻辑视口 `390 × 844`、状态和 fixture。首次默认态使用真实零历史；对比草稿有数据画面时明确使用对应 fixture。
2. 获取草稿手机内容与正式 Runtime 的真实截图；排除工作台外壳和草稿缩放。记录截图/可复现入口、差异、修改和复验结果。
3. 对比结构/阅读顺序、组件形状、Token/材质/比例、状态、交互五项。数据不同须区分真实业务口径与视觉偏差，不为匹配草稿造历史。
4. 在正式实现上应用 frontend-design 的体验检查。普通页默认 Quick；共享视觉语法、核心计时/打卡、数据图形和复杂 Overlay 使用 Focused，选择 3–5 张风险截图。机械执行全主题×全状态截图矩阵不作为每次迭代要求。
5. 检查显式 required boundary、节点唯一/可见/非零 bbox、合法 role 与完整 Token bindings。业务 DS 实例用稳定 inspectId，关键动作有 Action/Scenario/Checkpoint，prepare/readiness/reset 可重复。
6. 执行受影响的 typecheck、authoring lint、注册/布局/Token/行为检查和 Runtime 冒烟，记录结果；本页的 Delivery 与体验均通过才记已验收。

对比记录模板写入 implementation.md 的页面行下，使用：`页面/Variant/fixture → 主题/模式/视口 → 草稿与正式截图 → 五项差异 → 修正 → 验证命令/结果 → Experience 等级 → 遗留`。实现前不伪填通过。

## E：整体验证与正式交付

- E1 串起习惯与专注两条关键演示旅程，验证跨页状态、反馈、返回及复位；后台/重开/跨日/失败等只验证批准的代表场景，不以生产级恢复系统作为退出条件。
- E2 六种主题组合的主题探针、窄屏、减少动态效果及最终批次体验审阅；按 PBWork checklist 查 Token、Flex、Evidence、共享机制与导航。产品状态模型测试按真正风险编写，不为每页复制 Core fixture/e2e。
- E3 运行 `pnpm --filter @proto-bridge/pbwork typecheck`、PBWork tests、`pnpm test:e2e:runtime`、`pnpm docs:verify`、`pnpm ds:target-sync:verify`；完整交付批次运行 `pnpm verify`。失败明确范围，不能改文档声称通过。
- E4 通过生命周期工作流「待确定 → 已定稿」触发整原型 Capture。检查 Selection、Case、Coverage、Issue，固定主题包/摘要/取值表与声明时钟；Handoff/Delivery 绑定，MCP 按固定引用回读。采集未完成或存在 Block 不能宣称 final。
- E5 implementation.md 记录可复核的检查结果与固定产物引用；不提交 `.proto-bridge/store/`、`output/` 或 Target 构建产物。

## 调整与缩减

发现产品契约冲突时回到 design.md 闭合具体增量。技术问题先在唯一问题表定位到当前工作单元，修复影响该单元的最小范围。可以延后 Flutter 还原和非必要动效精修；保留三套主题、跨页演示状态一致、核心交互、逐页视觉检查、Evidence和正式定稿；不将轻量演示逻辑擅自扩大为完整业务建设。
