# ADR 0012：PBWork DS 是原型的基础而不是上限

- 状态：Accepted；第 6 项的阶段性限制已由 [ADR 0014](./0014-prototype-theme-packs.md) 替代。原文保留为当时的设计背景。
- 细化并部分替代：[ADR 0005](./0005-pbwork-foundation-and-component-boundary.md) 中“形状匹配时必须使用对口 PBWork 组件”

## 背景

同一业务原型在自由视觉探索与仅使用现有 DS 的方案对比中暴露出：只要按规则制作正式原型，所有原型都会收敛成 PBWork 的默认外观。追查后，原因不在缺几个组件或主题包，而在流程和规则本身：

- 两份 Skill 都要求 Agent 自行推断而不是提问，需求信息不足时，空白被 PBWork 现有外观填补；
- `frontend-design` 被定位为按需、从属的步骤，历史会话中只有用户点名时才被读取；
- “形状匹配时禁止重造组件”使组件形态全局共享，而原型的辨识度主要来自组件形态与构图，不在 Token 取值；
- 计划文档在视觉方向确定前就为每个元素指定了 DS 组件；
- 已有原型与草稿都以 PBWork 主题为起点，Agent 会沿用先例。

## 决策

1. **DS 是基础层。** DS 维护 Foundation 与基础组件；每个原型在其上形成自己的视觉身份。组件按 Promotion Mapping 自上而下选用：DS 原样、DS 公开变体、通用 DS 扩展、原型自有组件、外部资产、放弃或降级。
2. **风格与 DS 冲突时以风格为准。** 不为套用 DS 降级已批准方向；冲突记为 DS 缺口，作为 DS 演进输入。
3. **不放松的边界。** 手势、滚动、Overlay 和导航机制仍复用共享实现；原型自有组件遵守与 DS 组件相同的 Token-only、Flex-only 和显式 Evidence 规则；不通过私有 class 覆盖 DS 内部样式。
4. **先采访再设计。** 新原型和新视觉方向先完成字段固定、问法灵活的需求采访；风格难以用文字确定时询问用户是否先做风格草稿。
5. **定方向时必须应用 `frontend-design`。** PBWork 覆盖它“自行设定主题”与“只在有把握时展示想法”两条默认做法：主体取自已确认的 brief，并向用户呈现两到三个方向。
6. **品牌取值的现状如实记录。** Theme 仍只有全局 `light` 与 `dark`，现有 Token 无法表达的品牌值记为品牌层缺口，由用户决定等待原型主题包能力还是有记录地降级，不新增业务命名的共享 Token 或页内色板。

## 结果

- 原型可以拥有与 PBWork 不同的组件形态与构图，同时 Evidence 结构、Token 绑定与 Flutter 交付约束保持不变。
- DS 缺口在各原型的 `docs/implementation.md` 中可见，DS 扩展有了需求来源。
- 品牌取值由原型主题包承载，现行机制见[主题包解析模型](../architecture/theme-packs.md)。原规划与落地过程见[关键平台升级](../history/pbwork-platform-upgrade.md)，不再作为待实施依赖。字体不属于品牌层，统一使用默认字体栈。

## 后续落地

2026-10-17：品牌取值已由原型自有主题包承接，可继承基础包并声明包内多套主题与 light/dark 模式。第 6 项及结果中的等待/降级描述不再是当前限制。组件形态继续遵守本 ADR；解析与固定边界见 [ADR 0014](./0014-prototype-theme-packs.md)，字体仍使用默认字体栈。
