# 设计变更、按需采集与 Target 增量更新

状态：调研中，方案待敲定。记录日期：2026-10-23。调研代码基线：`1a8fca8`。

本文记录平台级问题、初步方向和后续决策项。yike 仅作为需求来源，不在此维护其业务实施进度。本文中的流程、数据记录与验证要求均为提案，不代表已有能力或现行 Contract；本轮只记录调研，不启动实现。

## 1. 问题与目标

原型已经定稿，Flutter 已实现部分页面后，作者可能需要调整局部组件、专属主题、公共 DS、设计基础或业务行为。需要回答：

1. 哪些页面、状态、主题和场景需要重新采集？哪些旧证据仍可使用？
2. Flutter 应修改哪些已有实现，哪些使用点需要回归，哪些尚未实现的范围只需记录新版要求？
3. 如何证明本次交付采用了新设计，并保留历史证据与既有 Target 业务成果？
4. 产品文档、固定 Evidence、公共 DS 与 Target 各自采用什么版本，发生冲突时如何呈现？

目标是建立“设计变更 → 影响范围 → 按需采集 → 固定交付 → Target 局部修改 → 回归与采用记录”的闭环。修改范围、采集范围、Target 实施范围和回归范围分别表达；影响广泛的变更仍可能需要大范围采集和验证。

## 2. 当前基线与已核实问题

当前行为以[产品工作流](../product/workflow.md)、[采集链路](../architecture/capture-pipeline.md)、[Evidence 模型](../architecture/evidence-model.md)、[Agent 消费指南](../guides/agent-consumption.md)和[Flutter Target 脚手架](../guides/flutter-target-scaffold.md)为准。

### 2.1 局部能力与正式产品路径尚未贯通

Core 的 Selection、稳定 Case/Scope、不可变 revision、Snapshot、Staleness 和 Handoff 已提供局部更新的底层基础。Snapshot 可以保留本次未触及的历史 slot，但保留不等于证明其仍适用于当前输入。

PBWork 当前正式“定稿并采集”仍采集整个 Prototype；CLI 的自定义 Selection/deliver 属于非正式诊断路径。不能把底层支持局部范围描述为 PBWork 已有正式增量交付。局部更新如何进入正式生命周期、确认范围与风险，是本提案需要设计的产品行为。

### 2.2 输入摘要较粗，缺少精确影响分析

- [Runtime 源码摘要](../../apps/pbwork/build/runtime-source.ts)覆盖 PBWork `src`、构建输入与 Core 源码等；排除 docs 和 drafts。无关原型或 Workbench 源码变化也可能改变摘要。
- [采集编排](../../packages/core/src/v2/capture/orchestrator.ts)以整体 Manifest 摘要、CaseKey 和 Scenario 计算复用输入；当前写入的依赖摘要主要为原型 Manifest 与 Screen 对应的全局 inputVersion。
- [Store](../../packages/core/src/v2/store/local-file-store.ts)已有依赖摘要比较和相同输入复用机制，但这些粗粒度输入不足以自动证明某个局部修改不影响其他 Case。

结论：目前能够判断整体输入变化，尚不足以可靠推荐最小重采范围。不能直接删除全局摘要保护来换取复用率。

### 2.3 新输入的同质量证据可能未被激活

[激活规则](../../packages/core/src/v2/resolver/activation.ts)在输入相同、等级和质量相同时复用旧 revision；其余候选只有等级或质量严格提升且无退化才晋级。新输入、同等级、同质量因此返回 `store-only`。

本轮以现有 `decideActivation` 和参考 fixture 直接调用复现：旧输入 `old-input`、新输入 `new-input`，相同完整 Scope、`instrumented-source-runtime` 和质量分数 1，结果为 `store-only`。[Snapshot 构建](../../packages/core/src/v2/store/snapshot-builder.ts)使用该激活规则，因此持续迭代存在采集成功却保留旧 active revision 的风险。

验证边界：已复现函数行为并核对调用链，尚未执行修改设计后的完整 PBWork 生命周期复现。后续需同时厘清防降级与新设计版本替换的语义，补充端到端验证；本轮未修复。

### 2.4 Case delta 不等于设计版本差异

现有 [buildCaseDelta](../../packages/core/src/v2/consumer-projection.ts)比较同一固定 Handoff 中 Screen baseline 与选中 Case，用于状态和场景差异消费。它没有提供两次设计定稿之间的正式差异合同。

尚需表达同一稳定 Case 在旧、新固定版本间的变化，以及新增、删除、重命名、Scope 变化、缺失证据和未知影响。不能把当前 `read_case_delta` 直接当作版本升级接口。

### 2.5 DS 同步、固定业务交付与 Target 采用状态未统一衔接

[DS 同步验证](../../scripts/verify-ds-target-sync.mjs)检查当前 Producer surface、Target 映射、生成主题/图标和同步基线；Handoff 则固定历史 Snapshot、revision 与 Catalog。它们回答的问题不同。

当 Producer 继续变化时，需要分别报告“Target 与当前 DS 的漂移”和“Target 是否符合指定历史交付”。目前没有串起本次设计变更、受影响业务页面和 Target 回归的统一记录。公共组件解析成功或 DS `synced` 也不能证明业务页面已经视觉验收。

Target 部分实现时，单个“最后使用的 Handoff”不足以描述不同页面/状态采用的版本与验证程度；未来需确定记录单位和失效规则。

### 2.6 文档首次导入已有，持续合并仍需设计

Flutter 脚手架已有显式 `target-docs.json`、导入来源与两端文件摘要，且拒绝覆盖已有非空工程。它解决首次导入；已有 Target 的产品文档更新仍通过临时生成、diff 与人工合并。

现有来源记录不与 Handoff 自动绑定。后续需要决定如何保留上次导入基准，比较“旧源文档、当前 Target 文档、新源文档”，并处理产品要求与固定截图之间的冲突。Target 的本地实施状态、已知缺口和评审历史保持各自所有权。

## 3. 初步方向与范围示例

以下为讨论方向，具体范围仍需结合依赖、实际使用与风险确定。

| 变更 | 候选采集范围 | Target 实施与回归 |
| --- | --- | --- |
| 原型局部组件外观 | 使用它的相关 Screen、状态与外观组合 | 修改局部实现，回归相关页面 |
| 公共组件尺寸、布局或行为 | 受影响使用点；行为变化追加相关 Scenario/Checkpoint | 更新公共实现与必要调用处，回归已实现使用点 |
| 原型专属主题取值 | 受影响主题、Token 使用和状态组合 | 更新对应生成主题，核验实际使用与显示 |
| 全局字体、间距或布局基础 | 可能覆盖大部分页面；关注换行、溢出和滚动 | 更新主题或公共实现，扩大页面回归 |
| 产品行为与状态 | 相关 Variant、Scenario 和跨页联动 | 修改业务逻辑和适用测试 |
| 仅文档表达修正 | 经确认不改变行为和外观时，无需重采像素 | 合并文档；要求变化另行评估 |

初步建议：

- 第一阶段由人和 Agent 给出有理由的影响清单，系统固定并展示范围与未知项；自动分析逐步接入。
- 以受影响 Screen 的完整 Case 为主要采集单位。布局、字号、尺寸变化优先保留整页上下文；Fragment 用于局部定位与检查，不将局部截图拼入旧页冒充新的完整观测。
- 公共组件修改明确区分实施与回归。修改一个公共文件可能影响多个已实现页面；尚未实施的页面记录新版要求，不因此提前实现。
- 旧证据只有在适用性获得支持时才作为当前范围的依据；无法证明不受影响的部分保留未知或扩大采集。
- 主题代表样本与规则派生继续遵守现有外观证据边界，不把代表实拍描述成全矩阵像素验证。
- Flutter 在现有工程上按需修改。业务成果、平台翻译和本地扩展由 Target 维护；生成器负责的文件与人工维护文件需要明确区分。
- Target 事实与采用/回归记录保持在 Target 或 Review 侧，不写回 Source Evidence。

## 4. 候选工作流与交付信息

候选流程：提出修改 → 判断所属层与设计确认范围 → 修改原型/DS/文档 → 形成影响清单 → Preflight 与确认 → 采集并核对激活结果 → 固定变更交付 → Target 局部实施 → 回归 → 记录采用结果。

候选交付信息包括：

- 旧、新基线的明确固定引用，及适用的源代码/产品文档版本；
- 新增、修改、删除和未确认的 Case/Scope；
- 组件、Token、主题、资产与产品要求变化；
- 各范围重新采集、复用或待确认的理由与证据来源；
- 所需公共能力与已知不兼容项；
- 实施范围、候选回归范围和未实施范围。

Handoff 继续提供固定事实与范围，Coding Agent 结合目标工程决定文件、API 和实施计划。上述信息是否由 Handoff 扩展、独立变更对象或其它投影承载，尚未确定；本文不预设 Schema、Tool 名称或命令。

## 6. 目标投入、主线与探索项

| 阶段 | 目标投入 | 依赖与退出标准 |
| --- | --- | --- |
| P0 正确性与方案收敛 | 完整复现激活问题；明确基线、生命周期、版本替换和失败语义；确定最小产品流程 | 已知问题有回归用例；决策与实现边界明确；后续修复证明新设计可被固定读取，失败不破坏历史 |
| P1 可控局部更新 | 人工/Agent 辅助影响清单、固定版本差异、正式局部交付、Target 采用与回归记录、文档合并基准 | 依赖 P0；真实局部变更完成闭环，未覆盖/未知/冲突可见，不要求自动最小范围 |
| P2 自动影响分析 | 细化依赖摘要，组合静态依赖、观察使用和作者声明，推荐重采与回归范围 | 依赖稳定的 P1 数据与验证；已知依赖变化不漏判，未知可回退，推荐理由可追溯 |
| 探索项 | 自动视觉差异辅助、成本估计、跨 Target 扩展、更细粒度安全复用 | 不作为 P1 前置；不得把推断或视觉相似当作已验证适用性 |

主线依次解决正确性、正式局部闭环和可靠的影响推荐。自动代码迁移、全自动文档冲突解决、最优最小采集集合不作为第一阶段承诺。

## 7. 验证与退出标准

后续实施至少覆盖以下平台场景；具体样例和执行方式在方案敲定时补充：

1. 同一 Case 修改设计后，成功的新输入证据能够按确定规则进入新交付，旧 Handoff 保持可读；失败和降级候选如实暴露。
2. 局部组件变化能更新指定范围；未触及范围分别呈现有依据复用、历史保留、stale 或未知，不由“未选择”推断无影响。
3. 公共组件修改能找到已实现使用点的回归义务；部分实现的 Target 不被错误标为全产品采用新版。
4. 全局主题/字体变化能够扩大采集与回归；缺少依赖依据时不会错误缩减。
5. 新增/删除状态、交互、主题或资产可在版本差异与交付范围中识别；固定引用、Catalog 和派生来源保持一致。
6. Target 本地文档存在修改时，上游更新可预览并合并，冲突可见；Target 状态与历史评审不会被源文档替代。
7. 分别报告采集完成、实施完成、回归覆盖和视觉接受，保留 deviation/unverified，不以同步状态替代验收。

能力落地时按[文档所有权](../maintenance/documentation.md)同步现行产品流程、Evidence/Capture/Target 合同、入口、Skill 与测试；已完成投入转入 history，未决内容继续留在本提案。

## 8. 范围缩减顺序

投入受限时，依次推迟：自动视觉差异与成本优化 → 跨 Target 扩展 → 自动影响推荐与细粒度复用 → 自动文档合并（保留明确基准和人工冲突处理）。

保留新证据正确激活、固定历史引用、未知/冲突披露、正式范围确认、Target 采用与必要回归记录。即使暂时扩大采集或人工核定影响，也不以省采集为由宣称未经证明的复用与验收。
