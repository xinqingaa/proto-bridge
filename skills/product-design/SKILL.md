# 产品设计

先完成产品设计，再进入实现。目标不是让用户填写一份冗长表格，而是把模糊意图整理成一套可判断、可体验、可实现的方案。

## 先判断请求类型

| 请求类型                                               | 处理方式                                         |
| ------------------------------------------------------ | ------------------------------------------------ |
| 新产品、新原型或新核心流程                             | 完成四个设计维度并获得确认后再实现               |
| 根导航、页面职责、核心对象、关键流程或视觉语言发生变化 | 先产出设计增量并获得确认                         |
| 单页布局、局部交互或局部视觉调整                       | 只补齐受影响的设计决策；若不影响结构，可直接实施 |
| 缺陷修复、文案修改、Token 微调、测试或证据维护         | 沿用既有设计，通常无需暂停实现                   |

不要仅凭改动文件数量判断请求类型。一个只改一处代码的导航调整，仍可能是结构性设计变更。

## 判断是否设计就绪

下列输入只能视为素材，不能直接视为完整设计：

- 只有主题、页面数量、功能清单或组件清单；
- 只有“高级”“简洁”“有设计感”等视觉形容词；
- 给出了导航名称，却没有说明各导航的职责与边界；
- 出现按钮、标签、筛选或入口，却没有明确触发后的结果；
- 用户目标、页面结构与交互行为彼此冲突。

逐项将设计信息判断为：

- **明确**：用户已经清楚决定；
- **可推定**：可依据上下文作出低风险、可逆的合理判断；
- **阻断**：不同选择会实质性改变产品方向、导航、关键流程或视觉语言。

遇到结构性的阻断项时，暂停实现。不要把问题原样退还给用户，也不要发送一长串问卷。应先整合现有信息，提出一套完整的推荐方案，说明关键取舍，然后只请求一次整体确认。只有确实存在两个同等合理且后果明显不同的方向时，才请用户选择。

## 四个必需设计维度

四个维度必须全部闭合，但文档不必机械地使用固定标题，也不要求固定篇幅。

### 1. 产品定义

明确：

- 目标用户与使用情境；
- 用户真正要完成的任务，以及当前阻力；
- 核心承诺与期望结果；
- 主要使用场景与核心闭环；
- 核心对象、关系和生命周期状态；
- 区分产品的设计原则；
- 非目标与明确排除范围；
- 能从原型或产品行为中观察到的成功信号。

优先用一句话表达产品承诺。页面和功能都应能回到这句承诺，否则应删减或降级。

### 2. 信息架构

明确：

- 内容和任务的层级；
- 每个根级导航的唯一职责；
- 根导航、局部视图切换、筛选和流程步骤分别属于哪一层；
- 哪些内容应成为页面、面板、浮层或流程；
- 入口、返回、深链和跨模块跳转关系；
- 每个页面存在的理由，以及明确不承载什么。

先按任务关系定义导航层级，再选择 Tab、分段控件、筛选条或普通入口。页面层级不等于 Tab 层级：二级页面不必有“二级 Tab”，内容分类也不应自动变成导航。

为每个视口设定导航层级预算。通常只保留一个根级导航和至多一个真正必要的局部视图切换；不要在同一视口叠加底部主 Tab、页面内一级 Tab 和更深层 Tab。若出现第三组横向切换，先重新判断它究竟是导航、筛选、流程步骤还是普通内容标题，并优先降级或移除。

拒绝职责重叠的导航。底部导航、页面内主标签和局部筛选不能同时争夺一级注意力。每个 Tab 必须切换到职责不同的内容、数据范围或任务状态；若切换后只有选中样式变化，或内容实际相同，应合并、改成静态标题或删除。不要为了满足预设数量而增加 Tab 或页面；数量应由用户任务决定。

### 3. 交互设计

明确：

- 每个页面的用户意图与操作优先级；
- 每个可见控件的实际效果；
- 操作触发前后可观察到的内容、状态或导航变化；
- 关键对象与页面的状态转换；
- 功能如何被发现，而不是只存在于界面上；
- 成功、加载、空、错误、校验、禁用和恢复状态；
- 确认、撤销、退出与中断恢复策略；
- 跨页连续性与返回后的状态保持；
- 键盘、滚动、安全区域与响应式行为；
- 如何证明一次操作已经成功。

一个页面应有一个主导目的，但可以保留多个合理操作。主操作、次操作和浏览入口要有清楚层级。

把原型视为可运行的产品切片，而不是静态页面集合。对每个可见交互至少明确“初始状态、触发方式、可见结果、是否持久化、如何恢复”。Tab、筛选、日期、按钮、列表项和开关都必须产生与其外观承诺一致的效果。若某项能力不准备实现，就不要把它画成可交互元素；不能用 Toast 或选中态掩盖内容没有变化的假交互。

### 4. 视觉编排

明确：

- 一句可执行的视觉命题；
- 每个页面的视觉焦点与阅读顺序；
- 字体层级、信息密度、节奏、留白和分区方式；
- 页面背景、平面区域、容器与浮层的表面策略；
- 颜色、强调和语义反馈的使用规则；
- 图片、图标、图表、形状与装饰的角色；
- 动效如何帮助理解状态变化；
- 深浅主题与目标视口下的表现；
- 每类页面采用何种顶部形态，以及由谁消费安全区域；
- 不同页面如何因任务不同而有意变化，同时仍属于同一产品。

组件清单不是视觉方向。避免“每段内容一个 Card”、所有区块同等强调、所有页面使用相同骨架。优先使用字体、间距、分割线、背景层级、对齐和局部色彩建立结构，再按需要使用容器组件。

把安全区域视为布局约束，不把它等同于 App Bar。根据页面任务选择顶部形态：需要返回、稳定标题或关键页面操作时使用标准 App Bar；以内容或沉浸焦点开场时，可使用安全区内边距、轻量工具行或自定义焦点头部。根级页面不要求统一添加 App Bar。应明确由壳层还是页面容器消费顶部和底部安全区域，避免遗漏，也避免双方重复添加间距。

## 形成最小但完整的设计产物

产物应服务于决策，不追求统一模板。对新产品或结构性重构，通常需要覆盖：

- 产品意图、范围与非目标；
- 核心对象和导航模型；
- 导航层级与各类切换控件的性质；
- 页面地图及页面职责；
- 关键流程、状态与恢复方式；
- 重要控件的触发结果与数据连续性；
- 视觉方向和逐页编排；
- 各类页面的顶部形态与安全区域策略；
- 已采用的假设、被否决的方案与仍需确认的决定；
- 可观察、可验证的验收信号。

对维护任务，只记录设计增量：什么不变、什么改变、哪些流程和页面受影响、如何验证。不要把小改动扩写成完整产品提案。

## 确认边界

进入实现前，确认以下条件成立：

- 从入口到核心结果是一条连贯旅程；
- 根导航职责互斥且容易解释；
- 同一视口没有互相争夺注意力的多层 Tab；
- 每个页面都有必要存在；
- 每个 Tab 和可见控件都有真实、可观察的效果；
- 关键状态、失败与恢复方式已定义；
- 视觉层级、表面策略、密度和强调规则可执行；
- 安全区域与目标视口已考虑，且没有为了安全区域强制套用不必要的 App Bar；
- 不再存在会改变整体方向的未决选择。

若这是新产品或结构性变更，向用户展示推荐方案并获得确认。确认可以是对整套方向的简短认可，不要求逐条签字。

## 交接实现

确认后，再把设计转换为当前项目需要的实现资料。通用产品设计 Skill 不规定设计系统名称、路由格式、测试框架、截图方式或证据结构；这些由仓库级规则和实现类 Skill 负责。

在 PBWork 原型中，可将已确认方向写入对应原型的 `requirements.md`，但不要强制固定章节、固定页面数量或固定组件配额。设计文档负责说明为什么这样做、用户如何使用以及界面如何组织；实现文档负责说明代码与验证方式。
